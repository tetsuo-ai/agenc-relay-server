# Authenticated terminal account root

An account recovering its root can verify a chain of signed identities locally.
The signatures establish continuity. The directory coordinator also knows
whether a successor already exists. This optional profile lets the recovering
client ask that coordinator to attest to its current head on the account's
original registered connection. A receipt describes one read. Publication
still validates the predecessor against the directory at commit.

## Negotiation

The capability name is `agenc.ag/root-head`. Its value is `v1.<profile>`,
where `<profile>` is unpadded base64url of SHA-256 over the following three
concatenated strings of bytes, in order:

1. ASCII `agenc-chat terminal root head profile v1`, without a terminator.
2. The raw 32-byte prospective initial-root profile hash.
3. SHA-256 of the exact committed UTF-8 bytes of this document.

The prospective initial-root hash already commits to the base federation
profile, ARC-MLS profile and initial-root specification. Federation peers may
explicitly select FHELLO version 3 with the 32-byte hash above. It retains
the version-2 initial-root operations, the ordinary authenticated hello layout
and the original companion ECAP negotiation. Both ends must select the exact
version and hash. The new operation requires a live version-3 link with
successful companion negotiation. A local coordinator requires its companion
directory and active signing authority.

The ordinary client CAP LS listing and unsolicited notifications retain their
existing registry. A client that negotiated the standard ARC-MLS prerequisites
sends an individual `CAP REQ :agenc.ag/root-head`. Successful discovery
produces `CAP NEW :agenc.ag/root-head=v1.<profile>` and then
`CAP ACK :agenc.ag/root-head` on that connection, following the same
target and prefix rules as the initial-root profile. A missing route, disabled
service or unsupported profile yields NAK. The client pins the value and
requires both messages before sending the request. Capability withdrawal,
loss of registration or replacement of the routing link invalidates its
use. Reconnecting requires fresh negotiation and account authentication.
Existing clients can use their ordinary commands on any supported listener.
Version-1 and version-2 links retain their previous wire grammars.

## Request and reply

A currently registered account sends one labeled command:

```text
@label=<label> EKEY PROVE ROOT-HEAD <challenge>
```

The challenge is the canonical unpadded base64url spelling of 16 fresh
operating-system random bytes generated by the client for this particular
read. The coordinator derives the sole eligible account, session generation,
network, recovery epoch and login receipt from the current authenticated
registration. The request has no account selector or uploaded object.
The request needs no attached device. Existing EKEY query rate, queue,
correlation, line and replay bounds apply.

For an authorized request the coordinator reads the head from the same
serialized committed directory that admits root publication. It requires the
current head's generation, fingerprint and final standalone RootIdentity
object ID. It also requires the original, successfully committed and
consumed OPAQUE login for this same live registered session. Its login binding
is SHA-256 of the exact 4,342-byte sealed `opaque_auth_complete` response.
The account service records that digest only after the successful durable
decision and binds it to the origin, connection, account and account session
generation that consumed the grant. The client obtains its comparison digest
from independently opening the matching pinned HPKE response on its own
connection. Fail closed when the live binding is unavailable, including
after restart or replacement. A new successful login establishes a new one.
No client or edge supplies the coordinator's login-binding value.

Only the active credential of the coordinator's current verified sequencer
set can sign a fresh proof. Check its network, validity at issuance, and
ownership of the matching private key. A pending successor and a retained
retired signing key cannot issue these proofs. The coordinator obtains UTC
from its trusted clock and computes `expires_at` as the lesser of
`issued_at + 30` and the credential's inclusive last valid second. Reject
arithmetic overflow. It signs the following exact TLS-presentation fields
without field names, vector prefixes or optional padding. Integers are
unsigned big-endian. Brackets give fixed widths in bytes.

```text
TerminalRootHeadTBS (290 bytes)
  uint16 version = 1
  network_id[32]
  recovery_epoch[16]
  account_id[24]
  uint64 account_session_generation
  login_completion_sha256[32]
  challenge[16]
  uint64 root_generation
  root_fingerprint[32]
  root_identity_object_id[32]
  uint64 sequencer_set_generation
  sequencer_set_digest[32]
  sequencer_credential_id[32]
  uint64 issued_at
  uint64 expires_at
```

Use the companion's ordinary Ed25519 `ArcSignatureInput` with the distinct
ASCII label `ARC-MLS/1 terminal root head` and the encoded TBS as content.
The 354-byte body is the TBS followed by the fixed 64-byte signature. The
360-byte version-1 ArcWireObject envelope uses the optional kind
`terminal_root_head(38)`, client token `ROOT-HEAD`. The new kind is
response-only. It is forbidden in uploads, recovery reference elements,
general object fetches and unsolicited projections.

The success reply is one companion object batch for `EKEY ROOT-HEAD`, with
the original label, one `ROOT-HEAD` object in one canonical EOBJECT fragment,
the ordinary fresh response scope and snapshot token, and `*` for the next
cursor. It has no operation metadata child. The ordinary labeled EKEY failure
is used for a guest, a stale origin or unavailable signing authority. An
account without a published root produces the existing labeled
`EKEY EMPTY IDENTITY`. A refusal, timeout or empty result confers no signing
or publication authority.

On the enhanced federation link use `prove_root_head(45)` in the companion
request with exactly the 16 unprefixed challenge bytes in encoded parameters
and no payload. The positive result is the ordinary object-page arm with one
response object and no cursor. The remaining valid outcomes are failure and
empty identity. Both directions require the negotiated enhanced profile and
bind the request and its single response to the original origin generation.
Exact federation replay can return the original receipt inside existing
finite retention. A replay never changes its expiry. The coordinator stores
no new permanent directory object or account record for an issued proof.

## Client acceptance

Compare every scope field to independently held state. The installation
must have accepted the descriptor for this network and epoch and verified
the complete sequencer credential chain or a chained update from its
previously accepted set. Require its exact current set generation, digest
and active credential ID. Verify the signature using that credential's
public key. Neither the response nor a caller chooses the verification key.
Require the credential to cover issuance and validation, and check
`issued_at <= now <= expires_at <= issued_at + 30`. Also enforce a local
monotonic deadline of at most 30 seconds from issuing the challenge.
An unavailable clock or an incomparable, partial or older set confers no
authority.

Require the same independently authenticated account, account generation,
login-completion digest, network, recovery epoch and unused original
challenge. Compare the returned generation, fingerprint and complete
standalone identity object ID to the locally reviewed predecessor. Verify the
identity and its required continuity signatures independently. Validate the
exact label, original socket, server, closing batch, fragment and object ID.
Discard the returned authority on scope loss, a changed set or root, socket
closure, stale or repeated challenge, timeout or a contradictory reply.
Never substitute an unsigned directory response when a proof is required.

A protected recovery signer uses distinct challenges for its initial review
and final approval. It keeps the same currently registered login and original
installation through the final durable signing checks. Recovery repeats
these checks after interruption. The coordinator serializes competing
successors at publication even if two clients observed the same predecessor.
Directory proofs create no authority to sign a root, activate local keys,
remove a roster, or consume a binding by themselves.

Keep command challenges, login digests, account and credential identifiers,
and receipt bytes out of application logs, metrics labels and diagnostics.
Carry them only on the authenticated request or its scoped, bounded result.
Availability failures during mixed-version rollout require a capable route
and a new authenticated read before protected signing can proceed.
