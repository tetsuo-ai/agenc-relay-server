# Prospective first-root service on Linux

## Creation and compatibility

The client can reserve the first public root while it creates an account. It commits to a client-held secret in the protected OPAQUE START. A successful FINISH binds that exact START to the newly allocated account. The coordinator writes the Guarded account, credential and reservation in the same transaction. The secret can authorize a private read or a single choice after a fresh account login. The root private key belongs to the client. The coordinator verifies the signed directory object through the existing publication path.

Existing clients see the original capability list. An upgraded client discovers support by requesting `agenc.ag/initial-root` on the current connection and waiting for the solicited NEW and ACK. An ordinary edge can publish the already selected signed object. The coordinator owns the decision for every route, including publication from clients that use the original protocol.

The first guarded account also establishes a minimum readable database format. A Linux test builds the previous accepted daemon, confirms that it still serves a legacy database, and starts both daemons on copies of the same guarded database. The older daemon refuses during recovery. The new daemon serves TLS on both a format-only snapshot and one containing a published account root. Run `bash scripts/test-initial-root-downgrade.sh` for this check.

## Permanent ownership and private response retention

Guarded account creation commits the account's permanent genesis policy and a private reservation alongside its ordinary OPAQUE credential. A private successful choice fixes one root fingerprint. Only the corresponding valid signed generation-zero directory object can advance it to Published. The coordinator retains its standalone object ID across later root rotations and exact-response expiration.

The local account service stores each registered READ or CHOOSE result once, in the protected request-result table. Its sealed response belongs to the original request, session and authenticated account. Every private disposition, including a denial, uses the same retention policy. A claimant can hold up to 128 exact results, and the coordinator can hold up to 16,384. Each compact index entry is charged to the shared process budget before durable admission and on reopening. One active ACCTROOT transfer also reserves its fixed encoded request buffer from that budget. The database and process limits can bind sooner.

The coordinator retains local exact bytes for seven days. Fresh requests can reclaim a mature result in the same atomic batch as their own response. An idle retention sweep retires at most 32 expired local results per batch. Delivery and cleanup require a wall clock consistent with the monotonic clock. A delayed first reply or retry can return the sealed bytes only before their authenticated expiry. An unexpired result retains its slot under pressure. A fresh authenticated request can reconcile the private choice after an earlier result expires. Federation requests also have their own origin sequence, exact reply and retention obligations.

The Linux regression fills both ceilings, exercises the exact expiry second, checks scope isolation and releases all process charges. A separate redb test reopens after a real HPKE choice and its atomic result, refuses premature cleanup under a disagreeing clock, commits expiration and reopens again. The chosen fingerprint and response count survive that second restart. The registered TLS daemon tests independently cover guarded account creation, ordinary-account denied access, signed directory publication and reopened private reads.

A Linux recovery test backs up one guarded account before and after a choice, dropping the TLS client before it opens the committed reply. After restoring each signed backup under a fresh recovery epoch and signing in again, the account can privately read the already chosen fingerprint. The earlier Reserved snapshot and any attempt to make a new choice in the changed epoch return Denied.

An edge answers a protected probe only while its exact configured coordinator link has completed the enhanced authenticated handshake and entered the active state. It binds that link generation to the soliciting physical client. A Linux daemon test leaves this client idle, stops the coordinator, receives CAP DEL and observes the connection close. A different client receives a normal base listing and NAK while the link is down, gets no unsolicited advertisement when it returns, and a fresh connection can request the reviewed token again.

A registered client may begin a private read while the coordinator is acknowledging its account declaration. The edge retains the exact origin, session, user, account, account generation and federation link that own the request. It forwards the sealed request after the matching acknowledgment. The edge tests exercise that interleaving, then change the account generation and the link independently and verify that each change prevents forwarding.

Two registered TLS clients each read the original reservation and simultaneously choose distinct valid fingerprints, while a third client on an ordinary edge submits another valid signed root. The coordinator returns one protected choice and one protected denial. A fresh sign-in finds exactly that choice, the other signed root is refused, and the directory accepts the chosen signed object. A final private read matches the published fingerprint and object ID.

When a durable write is pending, an opened private request stays in the bounded seal queue. Once the writer is idle, the service checks the registered caller and the immutable private account row before sealing and again at durable admission. An unrelated account write can complete in between. Replacing or deleting the original private row invalidates the prepared decision, including a read. The response counter and committed ciphertext remain subject to their own checks.

## Results on an authenticated federation link

The coordinator stores the exact outer result of each accepted guarded START or registered claim, including a denial. The result belongs to its issuing network, peer, origin, generation, operation sequence, request ID and request digest. A replay returns the original sealed bytes after checking the matched durable row and trusted time. Each result consumes one of 128 slots per origin, 1,024 per peer and 4,096 per coordinator. Pending operations share these limits with committed results. A full budget closes the requesting origin before admitting account work and preserves the other origins on that link. Existing results remain available for their specified lifetimes.

The coordinator samples trusted time again when staging the result. Its first authenticated read of the committed result starts a full seven-day interval, which covers a delayed write or a restart before the write was acknowledged. Observing the origin's deletion or fence adds a 24-hour interval. Retirement requires both deadlines to have elapsed. The sweep persists these observations and rechecks trusted time before deleting or releasing results. A delayed sweep can extend retention. The permanent account choice has its own durable owner.

The Linux redb test advances 400 seconds between intake and final storage admission and another 500 seconds before observing the committed result. It reopens the database after each recorded transition and exercises both possible deadline orders. A registered Linux TLS test fills all 128 slots for one origin with a repeated private read on distinct federation sequences. The next choice receives an ordinary service refusal, the requesting connection closes, a sibling already signed in through the same link sees the unchanged reservation and chooses, and a third client publishes that chosen signed root. The peer connection count stays unchanged. The aggregate peer and coordinator ceilings have separate in-process admission tests.

The coordinator commits the origin deletion before it sends a terminal response, acknowledges the matching deletion or retires the origin’s sessions. A redb regression rejects two successive writes, reconnects the affected edge and confirms the origin is still live on disk. A second peer commits its own declaration during recovery. After a successful retry, the original request receives the same terminal result without another write. The deletion survives restart and the sibling origin remains live.
